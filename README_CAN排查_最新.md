## 1. 之前为什么一直不通：把 FDCAN3 当成了电调那一路

两份交接文档对同一组寄存器数据的解读是**互相矛盾**的：

| 文档 | 对 FDCAN3 的解读 |
|---|---|
| `README_交接文档.md` | "只有 FDCAN3 的 TEC=0" → 所以 CAN 座接的是 FDCAN3 |
| `README_FOR_NEXT_AGENT.md` / `diag.c` | "TXBTO=0 → 这一路压根没发" → 假通道 |

**后者是对的，前者把因果关系弄反了。** 判据是这样：

- `TEC` 是**发送错误**计数。它只有在"帧真的被推上总线、但没人给 ACK"时才涨。
  所以 **TEC 涨 = 这一路有收发器、真的在往外发**；TEC=0 不代表它正常，只代表它没发。
- `TXBRP` 全是 1（8 帧都在排队）、`TXBTO=0`（一帧都没发出去）、`TEC=0`（连错误都没有），
  这个组合的物理含义是：**FDCAN 内核连第一个 bit 都没开始发**。
- 内核不发第一帧，只有一个原因：它认为**总线一直是显性（被压死）**。
  PD12/PD13 这条路上没有收发器时，RX 脚悬空被当成常低，正好就是这个现象。

所以三通道扫描的真实读法是：

| 通道 | 现象 | 真实含义 |
|---|---|---|
| FDCAN1 (PD0/PD1) | TEC=128 | 有收发器，帧发出去了，**没人应答** |
| FDCAN2 (PB5/PB6) | TEC=128 | 有收发器，帧发出去了，**没人应答** |
| FDCAN3 (PD12/PD13) | TEC=0、TXBTO=0 | **这条路上没有收发器**，帧从来没发出去 |

而原工程 `main.c` 恰恰只初始化了 **FDCAN3** —— 于是应用层的 0x200 控制帧
永远躺在队列里发不出去，电调当然一句话都不会回。

> 旁证：厂商自己的 `DM_MC02_Chassis.ioc` 里配的是 **FDCAN2（PB5/PB6）**，
> 这台板的 CAN 例程也是走 FDCAN2 的。

## 2. 已经改了什么

1. 新增 `Core/Src/can_probe.c`：**上电自动扫描 FDCAN1 / FDCAN2 / FDCAN3**，
   选一路能用的接着跑，用灯把三路结果报告出来。
2. `main.c`：不再写死 FDCAN3，改用探测结果；CAN 收发统一走 `Can_GetHandle()`。
3. `fdcan.c`：补上 FDCAN1（PD0/PD1，AF9）的初始化。
4. `can.c`：加 `Can_Bind()` / `Can_GetHandle()`；**去掉 RX 中断，只保留主循环轮询**
   （原来中断 + 轮询两条路都在读同一个 FIFO，属于重复处理）。

**没动的部分**：`rc_input.c`（SBUS）、`status_led.c`（WS2812）、SWA 控灯逻辑、
麦轮解算与速度环。`CHASSIS_SWA_LED_TEST` 仍然是 1。

## 3. 烧这个固件，然后看灯（一次就能定性）

烧 `firmware\DM_MC02_CANPROBE.hex`。上电时序：

| 时刻 | 灯 | 含义 |
|---|---|---|
| 0 ~ 0.75 s | 红→绿→蓝 各 0.25 s | 原有开机自检 |
| 0.75 ~ 3 s | **蓝灯常亮** | 正在扫描三路 CAN，别动 |
| 3 ~ 5 s | **依次 3 个颜色** | 第 1/2/3 个颜色 = FDCAN1 / FDCAN2 / FDCAN3 |
| 之后 | 回到 SWA 控灯 | 一档灭、另一档白（和以前一样） |

三个颜色的判读：

| 颜色 | 含义 | 下一步 |
|---|---|---|
| **绿** | 这一路收到了电机反馈 | 通了，就是它 |
| **黄** | 帧发出去了，但没有任何节点应答 | 收发器没问题，问题在**接线 / 供电 / 分线板** |
| **蓝** | 帧压根没发出去 | 这一路没有收发器（不是这条），或者 CAN_H/CAN_L 被短路拉死了 |
| **红** | 初始化就失败 | 告诉我，需要再看 |

> 注意：扫描时会占用约 2.2 秒，这期间遥控和灯的正常逻辑还没开始跑，
> 这是正常的。蓝灯一直亮不结束 = 卡在扫描里（不太可能，但出现了告诉我）。

## 4. 三种结果分别怎么办

### 4.1 FDCAN2 是绿的（最可能）

说明电调在 FDCAN2 上，总线本身是好的。之前不通纯粹是因为固件在跟 FDCAN3 说话。

接下来直接进入轮序标定：

1. `chassis_config.h` 里把 `CHASSIS_ID_PROBE_ON_BOOT` 改成 **1**，编译烧录。
   只接一块电调 → 上电 → 灯闪 N 下就说明这块是 N 号。
2. 四块都接好，把 `CHASSIS_SELFTEST_ON_BOOT` 改成 **1**（**先架空车轮**），
   烧录 → 1→2→3→4 号电机依次点动 1.2 秒。
3. 记下"哪个 ID 装在哪个角""正电流往哪边转"：
   - 位置不对 → 改 `chassis.c` 里 `wheel_linear[]` 的下标映射；
   - 转向不对 → 改 `CHASSIS_MOTOR_REVERSED_MASK`（bit0 = 1 号）。
4. 两个开关都改回 0，正常开跑。

### 4.2 两个黄色（FDCAN1/2 都是黄，FDCAN3 是蓝）

收发器是好的，**总线是通的但没有任何节点应答**。这时问题一定在线路上，按这个顺序查：

1. **电调到底通没通电**。C620 没上 24V 就不会回 ACK，现象和"断线"一模一样。
   先确认电调灯在闪（闪 1/2/3/4 次 = ID 1~4）。
2. **分线板到底有没有把 CAN 传下去**。`主板 → 分线板 → 4 电调` 这条链上，
   分线板是最可疑的一环：很多集线板只分了电源，CAN_H/CAN_L 是断的，
   或者只把 CAN 并联到了 4 个电调座、没有连到主板那根线。
   验证方法：把**一块** C620 的 CAN 线**直接**插到主板的 CAN 座上（不经分线板），
   24V 仍然从分线板取，再看这次上电的颜色。
   - 变绿 → 分线板的 CAN 没通，问题定位完成；
   - 还是黄 → 继续第 3 步。
3. **量电压**（上电状态，黑表笔接 GND）：
   - `CAN_H`、`CAN_L` 对 GND 都应该是 **≈2.5 V**（空闲隐性电平）；
   - 0 V 或 5 V = 短路 / 收发器坏 / 接反了。
4. **断电量电阻**：`CAN_H` 与 `CAN_L` 之间应该 **≈60 Ω**（两端各一个 120 Ω 并联）。
   如果是 ∞，说明总线上一个终端电阻都没有 —— C620 端通常自带，
   但分线板如果把它断开就没了，长线会直接通信失败。

### 4.3 三路全蓝

说明这块板子上三条 FDCAN 都没有对外收发器，或者引脚映射和中转文档不一样。
把三路的具体数字读出来（这一步需要 SWD）：

```
g_can_probe   @ 0x24000214   （12 个 uint32 × 3 路，见下）
g_can_probe_best @ 0x24000210
```

每路 12 个字，顺序是：
`init_ok, verdict, rx_total, rx_motor, rx_id_mask, tx_accept, tx_reject, tec, rec, psr, txbto, txbrp`

`verdict`：0=初始化失败 1=没发出去 2=能发没人应答 3=收到电机反馈

读法（PWLINK2 + OpenOCD）：

```powershell

$sc  = "C:\ST\STM32CubeIDE_2.2.0\STM32CubeIDE\plugins\com.st.stm32cube.ide.mcu.debug.openocd_2.3.400.202606220929\resources\openocd\st_scripts"
```

## 5. 想跳过扫描的话

`chassis_config.h`：

```c
#define CHASSIS_CAN_PROBE_ON_BOOT 0   /* 1 = 上电扫三路（默认）；0 = 直接按下面的用 */
#define CHASSIS_CAN_CHANNEL       2   /* 1 = PD0/PD1，2 = PB5/PB6，3 = PD12/PD13 */
```

调通以后建议**改成 0 + 2**，这样每次上电能省 4 秒，行为也固定下来。

## 6. 顺序建议（别跳步）

1. **先只上电、不接电调**，确认开机灯序和 SWA 控灯正常 → 说明固件跑起来了。
2. **接上电调（24V 要开）**，再上电看那三个颜色。
3. 颜色告诉你是"通道问题"还是"线路问题"，再往下走。
4. 通了之后**先把车架空**再跑自检/摇杆，别直接落地。
